# CreditGuard AI — AI-Driven Credit Risk & Responsible Lending Platform (MOCK UI)

> **This frontend is a mock.** `server.py` serves the demo web pages but
> generates predictions with hardcoded/random logic — there is **no real ML
> here**. The ML pipeline described below (sections 3, 9, 14) refers to a
> separate design that is **not present** in this folder; only `server.py`,
> `templates/`, `static/`, and `data/` exist. It is intended as a UI shell,
> not a functioning model.

A local-first, fully open-source prototype that estimates borrower credit
risk and demonstrates a full **Responsible AI** workflow:

```
PREDICT → SCORE → EXPLAIN → AUDIT → MONITOR → SIMULATE
```

> **This is a decision-support prototype, not a real banking approval
> system.** It never guarantees whether any individual will repay a loan.

---

## 1. Project Overview

CreditGuard AI takes permitted financial information about a borrower
(income, existing debt, loan amount, credit history, utilization, etc.)
and produces:

1. A calibrated **probability of default**
2. A demonstration **risk score (0–1000)**
3. A **risk category** (LOW / MODERATE-LOW / MEDIUM / HIGH / VERY HIGH)
4. A transparent **APPROVE / REVIEW / REJECT** recommendation
5. **Explainable AI reasons** (SHAP, with a labeled fallback if SHAP isn't installed)
6. **Anomaly detection** (Isolation Forest) as a review signal
7. A **fairness/bias audit** across any protected attributes present in the data
8. **Feature stability / drift monitoring** (Population Stability Index)
9. **Probability calibration** reporting (Brier score, ECE)
10. An interactive **What-If scenario simulator**
11. **Batch dataset assessment** with separate approved, review, rejected,
    anomalous, and unprocessed-row panels
12. Configurable **expected loss** (`PD × exposure × LGD`) with an explicit
  prototype LGD assumption
13. Batch data-quality reporting and auditable decision metadata
14. INR/USD input and display support, normalised to the model's INR base unit

## 2. Problem Statement

Lending decisions increasingly rely on machine learning, but naive
"black box" systems raise real concerns: unexplainable rejections,
hidden bias, and silent model drift. This project demonstrates how to
build a credit-risk model that is simultaneously **useful**, **explainable**,
**auditable**, and **monitored** — using only free, open-source tools that
run entirely on a normal laptop.

- **Backend:** Python 3.11+, Flask

## 6. Dataset Instructions

### Batch assessment uploads

Open **Upload Dataset** in the web app to process multiple applications at
once. CSV, JSON, XLSX, and XLS files are supported, with a maximum of 5,000
rows per upload. Each row should use the trained model's feature column names;
unknown columns are ignored and missing feature values are handled by the
preprocessor. The upload is scored by the existing model and is not used to
retrain it. Successful rows are also recorded in the local assessment history.

The result is split into **Approved**, **Review & Anomalies**, and
**Rejected** panels. Anomaly/data-quality flags are shown separately from the
model decision and are not an accusation of fraud. Rows that cannot be
processed are reported with their source row number.

### Currency support

The persisted demo model was trained on the synthetic dataset's INR prototype
units. Its monetary columns are `income`, `loan_amount`, `existing_debt`,
`credit_limit`, `credit_used`, `checking_balance`, and `savings_balance`.
Choose INR or USD on the assessment, batch, or Settings page. USD inputs are
converted once to INR before preprocessing; expected loss and displayed
monetary values are converted back afterward. Ratios (DTI, loan-to-income,
utilization), categorical values, and the model feature set are never
currency-converted. The rate is a configurable prototype value (`1 USD =
₹95.00` by default in `config.py`), not a live exchange rate.

**Option A — Use the German Credit dataset (recommended):**
Download a CSV version of the German Credit dataset (e.g. from the UCI
Machine Learning Repository or Kaggle) and save it as:

```
data/german_credit.csv
```

The loader automatically inspects the columns and looks for a target
column named one of: `target, class, credit_risk, risk, default, credit,
loan_default, creditability, y` (case-insensitive), and automatically maps
common encodings (`Good/Bad`, `1/2`, `0/1`, `Yes/No`) to `0 = good credit`
and `1 = bad credit / default`. If your file uses a different target
column name, set `MANUAL_TARGET_COLUMN` in `config.py`.

**Option B — No dataset available:**
If `data/german_credit.csv` is not found, the platform automatically
generates a **clearly-labeled synthetic demonstration dataset**
(`data/synthetic_credit_profiles.csv`) with a genuine (simplified)
statistical relationship between inputs and default risk, so every part
of the app can still be trained and demonstrated. This is **never**
presented as real financial data — check `model_metadata.json`'s
`is_synthetic_dataset` flag and the dashboard/monitoring page, both of
which display it.

## 14. Model Explanation

Three models are trained and compared: Logistic Regression, Random
Forest, and XGBoost (or its fallback). The best model is chosen using a
combination of **ROC-AUC** (discrimination) and **Brier score**
(calibration quality) — never accuracy alone. Probabilities are
calibrated with `CalibratedClassifierCV` (isotonic regression).

## 15. Responsible AI Explanation

- **Protected attributes are never used as model features** — only
  retained separately, when present, for fairness auditing.
- **Explainability:** every assessment shows the top risk-increasing and
  risk-reducing factors, in plain language, using real SHAP values when
  available.
- **Anomaly detection** is a review signal, not a fraud accusation.
- **Fairness audit** reports demographic parity and equal opportunity
  differences across any detected protected attribute, with a clear
  disclaimer that passing these metrics does not equal legal compliance.
- **Drift monitoring** (PSI) flags when incoming data no longer resembles
  the training population — again, a monitoring signal, not automatic
  proof the model is broken.
- **Decision engine** is a transparent, configurable policy
  (`config.py`), not a hidden ML verdict. Anomalous or low-confidence
  approvals can be routed to REVIEW, while deterministic rejections remain
  REJECTED.

## 16. Decision Policy and Expected Loss

The model target is normalised during training to `0 = good credit` and
`1 = bad credit / default`. Inference selects the probability for class `1`,
converts it to a score with `1000 × (1 - PD)`, and applies the configured
score policy:

- score `>= APPROVE_SCORE_THRESHOLD`: APPROVE
- score `< REJECT_SCORE_THRESHOLD`: REJECT
- otherwise: REVIEW

Anomaly and low-confidence rules may route an APPROVE to REVIEW, but they do
not mask a deterministic REJECT. Expected loss is calculated only when loan
exposure is available:

`Expected Loss = Probability of Default × Loan Amount × LOSS_GIVEN_DEFAULT`

`LOSS_GIVEN_DEFAULT` is a configurable prototype assumption, not a validated
portfolio recovery estimate.

## 17. Validation and Model Selection

Training uses a stratified holdout split. Candidate models are tuned with
bounded `GridSearchCV` searches and five-fold stratified cross-validation,
with preprocessing inside each CV pipeline. The final preprocessor is fit
only on training rows. Models are compared using ROC-AUC, PR-AUC, precision,
recall, F1, accuracy, and calibration metrics; selection combines ROC-AUC
and Brier score rather than optimizing accuracy alone.

## 16. Limitations

- This is a prototype trained on limited (possibly synthetic) data — it
  is not validated for real lending decisions and must not be deployed
  as one.
- Fairness metrics here are statistical monitoring indicators only, not
  a legal/regulatory compliance certification.
- The synthetic dataset (if used) encodes a simplified, illustrative
  risk relationship — it is not a substitute for real financial data.

## 17. Privacy Considerations

- No real banking credentials, passwords, or live bank connections are
  ever requested.
- All applicant data used in the UI is synthetic/demo data.
- The SQLite database stores only the fields needed for the demo
  (input features, computed scores, timestamps) — no unnecessary
  personal information.

## 18. Demo Workflow

1. Train the model: `python -m src.train_model`
2. Run the app: `python app.py`
3. Open the dashboard, click **New Assessment**
4. Fill in the borrower's financial details, click **ASSESS CREDIT RISK**
5. Review the score, category, and recommendation
6. Click **VIEW EXPLANATION** to see the "Why?" factors
7. Click **RUN WHAT-IF SCENARIO** to open the simulator pre-filled with
   the same inputs, tweak income/debt/late payments, and recalculate
8. Visit **Fairness Audit**, **Anomalies**, **Stability**, and **Model
   Monitoring** from the sidebar to see the full Responsible AI picture

## 19. Troubleshooting

| Symptom | Fix |
|---|---|
| "Model has not been trained yet" | N/A — this mock never trains a model |
| `ModuleNotFoundError` on startup | Run `pip install -r requirements.txt` inside your activated virtual environment |
| Port 5000 already in use | Edit the last lines of `server.py` to use a different port, e.g. `app.run(port=5001)` |
| Dashboard shows "0" everywhere | You haven't submitted any assessments yet — go to **New Assessment** and submit one |
| Fairness page says "unavailable" | Your dataset doesn't contain a recognised protected attribute column (see `PROTECTED_ATTRIBUTE_CANDIDATES` in `config.py`) |
